# External workload pre-screen

This document freezes external workload candidates **before** natural-workload evidence collection. It is a research pre-screen, not benchmark evidence, not a production claim, and not evidence that shared CHECK is useful for any project named below.

The canonical evidence rules remain in [`NATURAL_WORKLOAD_GATE.md`](./NATURAL_WORKLOAD_GATE.md). A completed natural-workload screen still requires at least 100 protected calls, `sample_type: natural_workload`, the best measured non-shared baseline, authoritative shadow validation, and the existing hostile evaluator. Static repository inspection never counts toward that floor.

## Pre-screen states

- `COLLECT` — the candidate survives static eligibility checks and is worth a falsification-first natural-workload collection. This does **not** predict `USE`.
- `REJECT_BEFORE_COLLECTION` — a stronger local/private/source-native path is already evident, or the workload requires fresh authoritative validation on every request.
- `INSUFFICIENT_EVIDENCE` — the path is plausible, but shareability, freshness, recurrence, public reproducibility, or the best-native comparison is not yet defined well enough to collect honestly.
- `FUTURE_NOT_DEPLOYED` — the interesting path is proposed or unmerged rather than a live workload.

A candidate can move only when new evidence changes one of those conditions. Negative results are retained rather than removed from this file.

## Collection plan frozen before measurement

### `structured_source_reads`: Agnix tool release watcher

This is deliberately an expected-hard case for SeenRelay rather than an expected win. The replay distribution comes from Agnix's live `tool-release-baselines.json`; it is not constructed to manufacture repeat hits.

Collection unit: one tracked tool's naturally scheduled version-source validation. The current Agnix implementation dispatches each tracked tool to exactly one of three source families: GitHub releases/tags, a public HTTP endpoint plus version regex, or the latest commit touching a configured GitHub path.

Before shared CHECK is compared, measure the same workload with:

1. the current local version baseline;
2. persisted `ETag` / `If-None-Match` or `Last-Modified` on the exact source request when available;
3. any provider-native cache already present in the execution environment.

A `304 Not Modified` is still an authoritative source-native validation and remains the baseline if it is the best non-shared path. Do not count commissioning or collector-debug runs toward the 100-call floor.

Kill criterion: if native conditional validation is equal or better on either marginal cost or latency, or natural exact recurrence is too sparse, classify the completed workload `DO NOT USE` rather than changing the workload.

### Local-only native-control census

[`scripts/agnix-native-control-census.mjs`](../scripts/agnix-native-control-census.mjs) and [`.github/workflows/agnix-native-control-census.yml`](../.github/workflows/agnix-native-control-census.yml) measure the best-native path before any hosted relay test.

This census is deliberately **not** `seenrelay-shadow-audit-v1`, does not emit `USE` / `DO NOT USE`, and does not satisfy the natural-workload admission gate. It makes zero SeenRelay `CHECK`/`OBSERVE` calls. The first complete persistent run is commissioning only; subsequent scheduled runs can count native-control calls while preserving the upstream tool distribution. The public artifact contains aggregate counts and timings only. Cache state uses salted opaque source keys and is not uploaded as the public artifact.

Only if this census leaves material residual latency/cost after source-native controls should the workload advance to the existing Shadow Proof and hostile evaluator. Do not seed the public relay from the replay and then count our own observations as independent reuse evidence.

## Fleet-validation gap

There is currently **no autonomous public `fleet_tool_validations` collection candidate** in this pre-screen.

Klangschalen is live and interesting but its full 45-repository workload is not publicly replayable without the token-visible repository surface. Velnor is publicly replayable, but commit-addressed local audit caching is already the stronger design for unchanged repository heads. Letta still mixes globally shareable runtime facts with account/backend-dependent probes. `feed-mcp` proves independent recurrence of GitHub Action metadata but is not itself a recurring natural production workload.

Do not turn any of those into `COLLECT` by dropping private/missing calls, disabling immutable caching, or treating a one-off migration audit as recurring traffic.

## Browser-extraction gap

No `browser_extraction_reads` candidate in this pre-screen currently survives the local/native/freshness/recurrence filter. That is a result, not a slot to fill artificially.

The first bounded browser-candidate search wave examined three mature families plus one residual forced-browser path:

1. `changedetection.io`: browser-backed recurring watches exist, but no public evidence found for exact cross-install recurrence under equivalent fetch semantics;
2. Huginn `WebsiteAgent`: recurring extraction exists, but no public evidence found for naturally repeated exact page identities across independent agents/installations;
3. Firecrawl-backed extraction: Firecrawl already exposes provider-native indexed-content reuse with `maxAge`, including `maxAge: 0` when freshness requires bypassing reuse. A Firecrawl-backed candidate must beat that provider-native control before shared CHECK can have incremental value;
4. groktocrawl forced-browser fallback: unlike the normal scrape path, `force_browser=True` skips the persistent Valkey cache and can invoke Playwright directly after a degraded lightweight pass. This is a genuine residual repeated-read surface, but it remains `INSUFFICIENT_EVIDENCE` until natural independent recurrence is demonstrated and the simpler local fix — applying the existing cache to that path without changing semantics — is shown not to dominate.

The search wave therefore stops with **no admitted browser collection candidate**. Reopen it only when new evidence identifies a deployed workload with natural exact recurrence, a shareable fetch identity, and material residual cost or latency after local/source/provider-native controls.

Do not start a three-workload natural gate until one independently defined browser/extraction workload survives pre-screening. In particular, do not weaken freshness requirements, disable a provider cache merely to create reuse, split one orchestration into fake independent callers, or manufacture repeated URLs.

Firecrawl's own current skill documentation states that repeat reads of the same URL can reuse recently indexed content and that `maxAge` bounds the age of that reused copy; `maxAge: 0` bypasses index reuse for freshness-critical reads. Treat that as a provider-native control, not as SeenRelay opportunity: [`firecrawl-build-scrape/SKILL.md`](https://github.com/firecrawl/firecrawl/blob/bbadeb87ba0d6425d761997d2b2fd59c95acf80f/skills/firecrawl-build-scrape/SKILL.md).

## Evidence boundary

GitHub documents authenticated conditional requests as a native polling optimization: most REST endpoints return an `ETag`; an unchanged authorized request can return `304 Not Modified`, and that response does not count against the primary rate limit. For GitHub-backed candidates, that path must be measured before SeenRelay can claim incremental value: <https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#use-conditional-requests>.

This pre-screen does not modify runtime behavior, enable reuse, create benchmark records, or change the three-way audit verdict contract. The only admissible benchmark evidence remains evidence accepted by the existing natural-workload gate and hostile evaluator.
