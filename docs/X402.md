# SeenRelay before x402 payment

SeenRelay can sit in front of an x402-paid validation without becoming a wallet, payment processor, or third payment policy.

The integration rule is simple:

> If an application already knows a source-backed value and is about to pay to revalidate that same fact, run SeenRelay `CHECK` before invoking the paid x402 call. If the caller's explicit freshness policy accepts the evidence, reuse the known value and never invoke the paid call. Otherwise let x402 run normally, validate independently, then `OBSERVE` the validated result.

This preserves SeenRelay's existing two-operation contract: `CHECK` and `OBSERVE`. No payment data is required by SeenRelay.

## Why preflight before the 402 handshake

The x402 protocol handles payment after a resource signals that payment is required. SeenRelay can avoid more work by running before the paid client is invoked at all. A reusable result therefore avoids the paid provider call, the 402 round-trip, and wallet signing.

x402's own spend-policy hooks should still remain in place. They protect amount, network, asset, seller and per-agent budget. SeenRelay answers a different question: whether the application needs to buy this validation again under its own freshness policy.

## JavaScript / TypeScript pattern

Configure your x402 client exactly as required by the x402 SDK, then put that paid call inside SeenRelay's existing validation guard.

```js
import {
  SeenRelayClient,
  reuseKnownOnSameObserved,
} from 'seenrelay';

// Configure this with the official x402 SDK for your wallet/network.
const paidFetch = /* wrapFetchWithPayment(fetch, x402Client) */;

const relay = new SeenRelayClient({
  clientHint: 'my-agent-fleet',
});

const getCurrentPrice = relay.protectValidation({
  fact: {
    subject: 'Example item price',
    predicate: 'price.current',
    source: 'https://merchant.example/item/123',
    locator: { scheme: 'source_key', value: 'price' },
  },

  // This function is reached only when validation is still required.
  validate: async () => {
    const response = await paidFetch('https://paid-api.example/item/123');
    if (!response.ok) throw new Error(`Paid validation failed: ${response.status}`);
    const body = await response.json();
    return body.price;
  },

  // Reuse is always caller policy. Omit this to stay in shadow mode.
  reuse: reuseKnownOnSameObserved,
  maxAgeSeconds: 300,
});

const price = await getCurrentPrice(17);
```

When `CHECK` returns acceptable `SAME_OBSERVED` evidence, `paidFetch` is not called. When SeenRelay returns `UNKNOWN`, `STALE`, `CHANGED_OBSERVED`, `CONTESTED`, times out, or is unavailable, the application's original paid validation path remains available according to the existing wrapper semantics.

## Keep x402 spend controls too

SeenRelay is not a substitute for x402 payment policy. Keep the payment client's own deterministic controls near the wallet. In particular, enforce the intended resource/tool, maximum amount, network, scheme, asset, recipient and per-agent/session budget before signing.

For x402 MCP clients, the official SDK exposes payment policies and an `onPaymentRequested` hook for this purpose. SeenRelay preflight should normally happen earlier, before the paid tool call is invoked; the x402 hook is a second safety boundary before the wallet signs.

## What SeenRelay does not receive

A normal SeenRelay preflight does not need:

- wallet private keys or signatures;
- payment authorizations;
- balances;
- recipient addresses;
- transaction hashes;
- x402 payment requirements.

SeenRelay receives only the same fact descriptor, known value, freshness window and optional observation metadata used by any other validation workflow.

## Failure semantics

- **SeenRelay failure:** fail open to the application's original validation path.
- **Payment refusal:** remains an x402/application policy decision and should not be swallowed by SeenRelay.
- **Paid validation failure:** propagates as an application validation error; no successful `OBSERVE` should be fabricated.
- **Reuse:** no paid validation is invoked and no new independent `OBSERVE` is emitted for that reuse.

## Adoption test

Start in shadow mode first. Measure, for the actual paid workload:

- full paid validations attempted;
- x402 payments/signatures actually created;
- eligible SeenRelay reuse hits;
- provider work and spend avoided;
- end-to-end latency;
- false or unsafe reuse according to the caller's policy.

Only enable bounded reuse when the application's own measurements and policy justify it.
